# nanobee × 三大命题：课题包装方案

> 一句话定位：**nanobee 是"存量系统 AI 化"的可控执行底座**——用极简微内核承载多租户隔离与全链路审计（数据治理），用插件 / 技能 / MCP 适配存量系统而不改存量系统（Agent 优化），用账本、模型路由与可观测性把"用哪个模型、花多少钱、效果如何"从经验判断变成可验证决策（模型与优化决策）。

本方案不发明新故事，只把仓库中**已经存在并可运行**的能力重新编排到三个命题下，每个论点都给出对应的代码位置或机制作为证据。

---

## 一、总体映射：三个命题，一个底座

| 命题 | 传统做法 | nanobee 的做法 | 承载机制（仓库证据） |
|------|----------|----------------|----------------------|
| AI 数据治理 | 事后补日志、日志里全是明文、多租户靠"约定" | **治理下沉到框架机制**：租户目录物理隔离、审计契约化输出、落盘前强制脱敏 | `ContextSandbox` / `ProcessWorkspace` / `audit_logger` 契约 v3 / `utils/redact.py` |
| 存量系统 Agent 优化 | 改造存量系统加接口，或写一次性脚本 | **零改造接入**：MCP 协议适配 + 工具插件 + 技能（知识资产）分层，存量系统只暴露既有能力 | `agent/mcp_manager.py`、`builtin/tool_*`、`kernel/skill_manager.py` |
| AI 模型与优化决策 | 拍脑袋选模型，成本靠账单反推 | **决策可证**：模型路由与降级、逐轮账本事实、OTel GenAI 语义一致审计、指标驱动调优 | `providers/`（含 `fallback_provider`、`model_presets`）、`TurnLedger`/`TurnReport`、`MetricsCollector` |

三个命题不是三套系统，而是**同一份基础设施的三个观察面**：数据治理决定"敢不敢用"，存量系统适配决定"能不能用"，模型与决策决定"用得值不值"。

## 二、方向一：AI 数据治理

### 2.1 命题本质

企业引入 Agent 后，新增了三类以前不存在的数据风险：

1. **越权访问**：Agent 以进程身份运行，天然能读到整个文件系统；一次 `../` 或一次 `cd` 就能穿透租户边界。
2. **不可归因**：出了问题无法回答"这一轮用了哪个模型、读了哪些工具、谁给的输入、为什么失败"。
3. **二次泄露**：审计、日志、错误信息、上下文压缩本身就是新的泄露面（密钥经异常文案回流到日志是典型）。

治理不是"多加几个 if"，而是**把边界做成机制，把事实做成契约**。

### 2.2 能力地图

```
数据入口            治理加工                      数据出口
─────────         ─────────────                ─────────────
用户消息    →   租户身份解析 / 存储键归一   →   审计契约（OTel GenAI）
工具调用    →   路径沙箱 + 进程工作区约束   →   结构化日志（Trace ID 贯穿）
附件/媒体   →   SSRF 校验 + 白名单根        →   指标聚合（token/延迟/错误）
技能资产    →   SoulGuard 完整性校验        →   脱敏后落盘
```

### 2.3 四个可讲的技术点

**（1）租户隔离是物理的，不是逻辑的**

- 每个用户拥有独立 `context_root`，会话、记忆、审计、cron、插件临时目录全部落在各自目录下（`self.tmp` / `self.context_root` 按请求注入，插件不持有全局路径）。
- 路径解析一律走 `ContextSandbox` 多根白名单：写操作仅限本租户 `context_root`，读操作覆盖技能目录等只读根，`../` 逃逸在解析阶段被拒绝。
- `execute_shell` 走 `bwrap` 挂载命名空间：`--tmpfs $HOME` 掩藏主目录，`ProcessWorkspace` 与路径校验边界解耦，只把"本次允许的进程可见目录"交给工具层。
- **这是 P0 生死线**：设计目标是"哪怕所有插件崩溃，Alice 也读不到 Bob 一字节"。这条边界不依赖任何业务代码自觉。

**（2）审计是真值契约，不是启发式推断**

`audit_logger` 是 `TurnReport` 结账单的第一个消费者，只做"事实 → 契约 dict"的纯映射，插件侧零观测逻辑：

- 字段命名对齐 **OTel GenAI Semantic Conventions**（`gen_ai.usage.input_tokens`、`gen_ai.response.finish_reasons`、`gen_ai.tool.call.id` 等），自有概念统一 `nanobee.*` 前缀。
- token 用 provider 实测值，`nanobee.usage.estimated` 恒为 `False`——**不允许估算冒充计量**。
- `trace_id` 采用 W3C 32 位 hex，与日志流同源，一次 turn 可从审计行串到应用日志。
- 一行 JSONL = 一个终态 turn，内嵌 `tool_spans`（含原生 callId、耗时、status、参数摘要），单行即可还原整条链路。
- 该契约是 v3，语义变更是破坏性升级——说明它被当作**对外承诺**维护，而不是随手打的日志格式。

**（3）脱敏发生在落盘之前的唯一一点**

`utils/redact.py` 是脱敏与错误串归一化的**单一处理点**：审计侧与用户可见侧共用同一规则，避免"审计脱敏了但通知里裸奔"的规则漂移（这曾是真实缺陷）。截断顺序被显式规定为**先脱敏、再截断**，因为截断边界可能切断 `key=value`，让掩码失效。

**（4）治理对象包含"知识资产"本身**

技能（SKILL.md）是用户与管理员的知识资产，因此也在治理范围内：

- 三级技能（内置 → 实例 → 用户）同名去重，优先级明确，避免"谁覆盖了谁"说不清。
- `SoulGuard` 对 `core.md` 做 chmod 444 + 写入拦截 + SHA-256 校验三层保护，防止人设/红线被运行时篡改。
- 渐进式注入（默认只注入元数据 + 绝对路径，`full_inject: true` 才全量）从机制上缩小了提示词注入面。

### 2.4 交付物与量化目标

| 交付物 | 形态 | 验证方式 |
|--------|------|----------|
| 租户隔离基线 | 沙箱 + 进程工作区配置 | 越权用例全部被拦截（负向测试） |
| 审计契约 v3 | JSONL + OTel GenAI 字段 | 单行可还原一轮完整链路 |
| 脱敏单一真相源 | `utils/redact.py` | 密钥类样本零残留 |
| 治理运行手册 | `docs/` | 运维可按手册取证 |

**目标指标（待实测填充，不预设结论）**：越权尝试拦截率 100%（负向用例）、审计字段完整率 100%、密钥落盘零残留、单 turn 取证耗时从"翻多份日志"降到"读一行 JSONL"。

## 三、方向二：存量系统 Agent 优化

### 3.1 命题本质

存量系统（ERP、EBS、工单、报表、钉钉/企微）的共同约束是：**不能改、不敢改、改不起**。因此 Agent 化的关键不是"给存量系统加智能"，而是**在不触碰存量系统的前提下，把它的既有能力安全地借给模型**。

这件事的难点从来不是"调用"，而是三件事：能力如何被发现、权限如何被约束、失败如何被解释。

### 3.2 三级接入路径（按侵入度从低到高）

| 层级 | 手段 | 侵入度 | 适用 |
|------|------|--------|------|
| L1 | **MCP 协议适配**（stdio / SSE / Streamable HTTP） | 存量系统零改动，只需一个适配进程 | 已有 API / CLI / 数据库的成熟系统 |
| L2 | **工具插件**（`nanobee/builtin/tool_*` 或实例级 `plugins/`） | 只写插件，不碰存量代码 | 需要业务封装、鉴权注入、结果归一化 |
| L3 | **技能资产**（SKILL.md + 脚本） | 纯知识/流程，无需重新部署 | 流程规范、口径说明、脚本编排 |

关键设计：**L3 是"知识"，L1/L2 是"能力"**。业务口径写在技能里由 LLM 按需读取（渐进式注入），而不是硬编码进框架——这直接决定了同一套底座能否复用到第二个、第三个存量系统。

### 3.3 支撑"零改造接入"的四个机制

1. **白/黑名单与工具级过滤**：插件级禁用（整个插件不加载）与工具级隐藏（插件加载但工具不可见）是两种语义，分别对应"这套系统不该接入"和"这个动作不该开放"。
2. **工具执行前的上下文注入**：框架在每次工具执行前注入 `channel/chat_id/user_id`，插件不需要自己猜"当前是谁在调我"，多租户天然成立。
3. **计划任务（cron）**：存量系统的日报、对账、巡检可以脱离对话触发，Agent 从"聊天框"变成"值班员"。
4. **子代理（subagent）**：复杂流程可拆分为受限子任务并行执行，主代理只做编排，降低单轮上下文压力。

### 3.4 已具备的接入样例

- **EBS / 数据库类**：通过 MCP 封装既有 SQL 网关，Agent 只看到"查询/校验"这类语义化工具，物理表与账号不进提示词。
- **钉钉类**：`channel_dingtalk` 作为通道（人机入口）已具备流式卡片、媒体读取白名单、群聊/单聊区分；同域内的业务系统可通过 MCP 侧接入，形成"人在钉钉、活在系统"的闭环。
- **HTTP 类**：`channel_http` 提供 OpenAI 兼容的调用面，便于把 Agent 嵌进既有门户或工作流引擎，而不要求对方改造前端。

### 3.5 交付物与量化目标

| 交付物 | 验证方式 |
|--------|----------|
| 存量系统接入 SOP（L1/L2/L3 选择树） | 新系统按 SOP 可在数天内跑通 |
| 适配层模板（MCP server / 工具插件 / 技能包） | 模板可直接复制，不需要读框架源码 |
| 权限矩阵（谁能用哪个工具、哪个前缀） | 配置即生效，且有负向用例 |

**目标指标**：存量系统改造量 = 0（代码零改动）；单系统接入周期从"周"降到"天"；新增能力不重启框架（技能热加载）；任一接入可配置级回滚（禁用即下线）。

## 四、方向三：AI 模型与优化决策

### 4.1 命题本质

模型选型与调优最常见的三种"伪决策"：

- 用最贵的模型保效果 → 成本失控，且没人能证明贵在哪；
- 用最便宜的模型省成本 → 效果回退不可归因；
- 调完 prompt 说"感觉好多了" → 没有基线、没有回归、无法复现。

**要把"决策"变成可辩护的动作，必须先有事实，再有实验，最后才有结论。** nanobee 提供的是事实层与实验层。

### 4.2 事实层：逐轮账本

`TurnLedger` / `TurnReport` 是"记账本"模式：runner 在**已经算出事实的代码行旁**追加 O(1) 记录，只记索引、计数、耗时、ID，不拷贝消息内容。

可回答的问题：

- 这一轮迭代了几次？每轮的 `finish_reason` 原值是什么？
- token 是 provider 实测还是估算？（契约强制实测）
- 工具调用了几次、哪些失败、耗时分布如何？
- 这一轮为什么退出（正常 / 达到迭代上限 / 异常 / 被取消）？
- 是否存在上下文注入？注入了几条？

这些问题过去要靠"读日志 + 猜"，现在是**一个结构体**。

### 4.3 实验层：模型路由与降级

- **Provider 抽象**：Anthropic / OpenAI 兼容 / Azure OpenAI / Bedrock / GitHub Copilot / OpenAI Codex / Responses API 均实现同一接口，切换模型不改业务代码。
- **模型预设（model_presets）**：把"模型 + 生成参数"打包成命名预设（如 `fast` / `deep`），按场景引用。
- **降级链（fallback_models）**：主模型失败按序尝试，降级不是硬编码策略，而是配置。
- **可调参数全部外置**：`max_iterations`、`max_messages`、`memory_store_threshold`、`temperature`、`context_window_tokens` 等都在 `nanobee.yaml`，不在代码里写死。

> 这条与项目铁律一致：框架只提供机制，不持有策略。**阈值、条数、超时都是策略性数值，必须由使用者配置或由 LLM 决策**——框架不替业务拍板。

### 4.4 决策闭环

```
观测（账本 + 指标 + 审计） → 归因（失败分类 / 工具错 / 上下文超限）
        ↓                                   ↓
发布（配置/预设/技能热更新）   ←   实验（A/B 模型、调整阈值、补技能）
        ↓
回归（自动化测试 + 基线对比）
```

- **可观测性**：`MetricsCollector` 进程内聚合 token、延迟分布、工具调用、错误计数；结构化日志（JSON）可被 Promtail / Filebeat 采集；Trace/Span ID 对齐 W3C Trace Context，可直接对接 OTel 生态。
- **回归闸门**：仓库自带测试套件（81 个测试文件、1500+ 测试用例），任何框架改动必须对比基线，策略性改动要求"先评审、再动手"。

### 4.5 交付物与量化目标

| 交付物 | 验证方式 |
|--------|----------|
| 成本看板口径（token/轮次/工具） | 从审计 JSONL 直接聚合，口径唯一 |
| 模型选型实验报告模板 | 同一批任务在多预设下的账本对比 |
| 降级与熔断配置基线 | 主模型故障时自动降级且用户可感知 |

**目标指标**：单任务 token 成本可归因到轮次与工具；模型切换成本 = 改一行配置；劣化可在一个回归周期内被发现（而非用户投诉后）。

### 4.6 优化纵深（一）：MCP 规模化下的 Token 经济学

nanobee 已在生产实例上运行，优化不再停留在"换模型"，而是进入**结构性成本**：MCP 服务器工具越多，每轮 prompt 背的 JSON Schema 越重，且一轮内每次迭代都重复计费——这部分开销与问题复杂度无关，是纯固定成本。

实测基线（本仓库内置 14 个工具）：定义总量 8268 字符 ≈ 3.3k token；按同一口径推算，一个 50 工具的企业级 MCP server ≈ **6k–16k token/次请求**，迭代 5 次即重复 5 遍。

四层优化（按性价比排序，全部配置化、可回滚）：

| 层级 | 手段 | 现状 |
|------|------|------|
| L0 | 缓存友好：稳定排序 + 断点打在 builtin/MCP 边界与尾部 + `cached_tokens` 归一 | **已具备**（本次优化的地基） |
| L1 | Schema 瘦身：去 `$schema`/`title`/`examples`、描述截断、清空无效分支 | 待做，风险低 |
| L2 | **延迟加载**：内置全量 + MCP 目录（name + 一行摘要）→ `tool_search` 检索 → 命中装载 → 自动激活执行 | 核心收益项，净省 60–75% |
| L3 | 结果侧：截断 + 大结果落盘 + 历史剪裁 | **已具备**，缺统一度量 |

关键洞察：**动态工具列表每变一次，尾部 prompt cache 就 miss 一次**。所以延迟加载不能做成"每轮重算工具集"，必须"目录段稳定前置 + 激活段只追加"。省 token 与省缓存钱是同一道题。

同时补齐连接侧"第二成本"：并发预连接、目录与连接解耦（断连仍可见能力清单）、重连时原子替换工具集（避免 LLM 看见半套工具）。

### 4.7 优化纵深（二）：A2A 的边界与前置条件

```
MCP = Agent → Tool（用能力）      A2A = Agent → Agent（找能力）
```

nanobee 的落点复用现有扩展点，不改内核：入站做 A2A Channel 插件（Agent Card + 任务端点），出站做 `a2a_send` 工具插件（发现 → 委派 → 回调），能力声明直接复用三级技能机制。

但 A2A 有三条硬前置，缺一不可：**租户边界（出站字段级白名单）**、**trace 传播（`traceparent` 已有 W3C 编解码基础）**、**预算与幂等（防递归委派烧穿成本）**。因此建议排在 MCP 目录化之后——"找 agent"与"找工具"共用同一套预算与归因基础设施。

> 完整设计（成本模型、字段级方案、A/B 实验设计、风险与回滚）见 [MCP 工具规模化下的 Token 经济学](mcp_tool_token_optimization.md)。该文档为**待评审方案**，未改动任何框架代码。

## 五、为什么底座是"微内核"而不是"一个大 Agent"

这是本课题在技术评审中最容易被问的问题，答案必须结构化：

1. **治理需要边界，边界需要内核**。沙箱、租户解析、脱敏、审计这些事如果交给业务插件自觉执行，等于没有治理。它们必须在消息流水线的固定切面上强制执行。
2. **接入需要扩展点，扩展点需要稳定契约**。存量系统千差万别，唯一稳定的抽象是"通道 / 工具 / 技能 / Hook"四类扩展点。
3. **决策需要事实，事实需要单一来源**。如果每个插件各自统计 token，口径必然漂移（这正是审计 v2 的教训：历史污染计数、注入归因错位、token 字符估算失真）。
4. **框架不持有策略**（框架无知论）：框架不知道"记忆"是什么、不知道哪些技能该全量注入，只读 `full_inject` 标记。这是三个命题能复用到不同业务域的前提——**同一底座，不同策略**。

## 六、三阶段路线图

> 以下为推进节奏建议，具体日期按立项批复时间对齐。

**阶段一：底座与治理（已有基础，补齐取证）**
- 固化租户隔离基线（负向用例全覆盖）
- 审计契约 v3 稳定输出 + 取证手册
- 成本/延迟看板口径落文档

**阶段二：存量系统规模化接入**
- 输出 L1/L2/L3 选择树与三类模板
- 完成 2–3 个存量系统接入（含一个数据库类、一个办公协同类）
- 权限矩阵与回滚演练

**阶段三：优化决策闭环**
- 补齐结构性成本度量：`tool_tokens_per_request`、`cache_hit_ratio` 进账本
- L1 Schema 瘦身 + L2 MCP 工具目录化（`tool_search` + 自动激活）
- 模型预设 + 降级链的生产基线
- A/B 实验报告模板与一次真实调优复盘
- 回归闸门接入 CI（改动即对比基线）

- 入站 Agent Card + 出站委派工具
- 三条硬前置先行：租户边界、trace 传播、预算与幂等

## 七、成效度量体系

**北极星指标**：单位业务任务的全链路成本（token + 时延 + 人工干预次数）。

| 维度 | 指标 | 数据来源 |
|------|------|----------|
| 治理 | 越权拦截率、审计字段完整率、密钥落盘残留数 | 负向用例 + 审计 JSONL 抽检 |
| 接入 | 存量系统代码改动量、单系统接入周期、回滚耗时 | 接入台账 |
| 决策 | 单任务 token、工具定义 token 占比、缓存命中率、平均迭代数、工具失败率、降级触发率 | TurnLedger 聚合 |
| 稳定 | 回归通过率、异常退出占比、首轮 MCP 工具可见率 | 测试基线 + 审计 `exit_reason` |

护栏指标（任一恶化即暂停推进）：租户隔离负向用例失败、审计缺字段、工具调用成功率下降、成本单任务上涨超过预设阈值。

## 八、风险与边界

| 风险 | 应对 |
|------|------|
| 把"框架能力"讲成"业务成果" | 申报口径严格区分**已实现机制**与**待验证效果**，后者必须标注"目标" |
| 治理过度导致接入成本反弹 | 三级接入路径，能用 L3 技能解决的不写插件 |
| 模型能力波动影响结论 | 结论必须绑定账本事实与回归基线，不接受"感觉更好" |
| 单点最优、全局更差 | 以北极星指标（全链路成本）而非单指标（如 token）评估 |
| 安全边界被业务插件绕过 | 边界在内核层强制，不依赖插件自觉；插件崩溃不影响隔离 |

## 十、申报口径速用版本

**100 字版**：nanobee 是面向存量系统的 AI Agent 微内核底座。内核级租户隔离与 OTel 一致性审计解决"AI 数据治理"，插件/技能/MCP 三级适配实现存量系统零改造接入，逐轮账本与模型路由把"选模型、控成本、调效果"变成可验证决策。

**300 字版**：在三个命题上，nanobee 提供同一套基础设施的三个观察面。数据治理侧，租户数据物理隔离、路径与进程双重沙箱、审计以 OTel GenAI 契约输出且 token 取实测值、脱敏在落盘前单点执行，使"敢不敢用"有据可查；存量系统侧，按"技能（知识）→ 工具插件（封装）→ MCP（协议）"三级路径接入，存量系统零改动、能力可配置级回滚；模型决策侧，多 provider 统一抽象、预设与降级链配置化、逐轮账本记录迭代/耗时/工具/退出原因，并针对 MCP 工具规模化带来的固定 token 开销，设计了"缓存友好 → Schema 瘦身 → 工具目录化按需装载"的分层优化（延迟加载净省 60%+），使成本可控可证。技术主张是"框架只给机制、不持有策略"，因此同一底座可复用到不同业务域而不被业务语义绑架。

**5 分钟口头稿结构**：先讲一个真实约束（存量系统不能改）→ 再讲一个真实风险（Agent 天然越权）→ 再讲一个真实痛点（成本与效果说不清）→ 最后说明三者共用一套内核机制，并给出可现场演示的证据（审计一行 JSONL、越权用例被拦截、改一行配置切模型）。
