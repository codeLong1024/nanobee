# 记忆管理（回答前必执行）

> **这是默认记忆策略模板。** 用户可以通过创建同名 `skills/_memory/SKILL.md` 完全替换它。
> 当用户表达对记忆行为不满或想调整策略时，你必须主动引导：
> 「当前的记忆策略是系统默认的。我可以帮你在 `skills/_memory/` 下创建一个自定义版本，
>   完全替换这套规则。你想要调整哪些行为？比如存什么、何时压缩、保留多少条历史等。」

## 回答前检查清单（不可跳过）

### 1. 检查是否需要存储
- 本轮对话是否有新事实？（用户偏好、决定、个人信息、重要上下文）
- **如有 → 在给出回答之前，先调用 write_file 追加到 `memory/facts.md`**
- 追加格式：`- [YYYY-MM-DD] 事实描述`
- **去重检查**：如果已有相同事实，跳过不追加
- **无新信息 → 跳过，直接回答**

### 2. 检查是否需要查询
- 用户问题是否涉及过去信息？
- **如是 → 先调用 read_file 读取 `memory/facts.md`，再回答**

### 3. 回答用户
- 完成上述检查后，给出正常回答
- **如果在第 1 步写了记忆，回答中不要重复提及记忆操作**

## 记忆压缩（按需触发）

当 Runtime Context 显示 `Conversation: ~X tokens (Y%)` 中 token 占比 >70% 时：
1. 覆盖 `memory/facts.md` 为精简摘要（**删除过时、重复、已失效的事实**）
2. 阅读早期对话历史，自行编写一份压缩摘要（100-300 字），覆盖：关键决策、用户偏好、重要事实、未完成任务
3. 调用 `consolidate_history(summary="你的摘要", keep_last_n=8)` 归档旧消息并注入摘要
   - `consolidate_history` 会自动将摘要存入 .consolidation.jsonl 归档，裁剪旧消息，并在开头注入 system 消息
   - 仅在无需保留摘要的紧急清理场景使用 `trim_history(n)`

### 事实清理规则

压缩时，必须删除以下事实：
- **过时信息**：已被新事实覆盖的旧版本（如旧 API Token、旧配置）
- **重复信息**：相同事实的不同表述
- **临时信息**：仅与当前会话相关、无长期价值的内容
- **闲聊内容**：用户非业务相关的日常聊天

## 违规后果

如果你忘记存储重要事实，用户下次提问时会丢失上下文。
