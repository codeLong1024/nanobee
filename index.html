// Core Philosophy

反「大而全」的微内核

大多数 AI Agent 框架是"大而全"的——自带记忆策略、梦境调度、人设漂移检测，但你可能用不上，或者想用自己的方案。nanobee 反其道而行：框架聚焦核心基础设施，业务逻辑通过插件实现，技能管理等高频核心能力直接内置于内核。

核心与插件分离Separation

高频核心能力（技能发现与注入）内置于 kernel；业务逻辑（审计、工具过滤）留给插件。

框架无知论Ignorance

框架不知道"记忆"是什么、不知道哪些技能该全量注入，只读 SKILL.md 的 full_inject 标记，按标记执行注入策略（全量 or 渐进）。策略决策由 LLM 自主完成。

隔离绝对论P0 · Isolation

P0 唯一生死线——物理隔离 + 沙箱拦截。哪怕所有插件崩溃，Alice 也绝无法越权读取 Bob 一字节文件。

Hook 侵入论Composable

在消息流转的所有关键切面留下接口，让插件劫持上下文、动态修改工具列表、监听生命周期。

// Core Mechanisms

覆盖 Agent 完整生命周期的机制

message-pipeline
用户输入 → ChannelPlugin → CommandRouter(拦截 / 命令) → NanobeeKernel → AgentLoop(状态机)
                                                                                  │
      RESTORE → BUILD(system prompt) → RUN(LLM + 工具迭代) → SAVE → RESPOND
🔀PIPELINE

消息流水线 · 6 态状态机

  • 命令拦截：/ 开头命令（/stop·/new·/status·/help）在获取用户锁之前拦截，零 token 消耗；/stop 可打断死锁 turn
  • 异常恢复：任一状态处理器异常时填充错误上下文、跳过 SAVE、直接进入 RESPOND 流式回复
  • 双层 Hook：5 个迭代级 Hook 覆盖工具执行前后；4 个 run-level Hook 包裹整个迭代循环
🛡️SECURITY

感知与安全

  • ContextSandbox：多根白名单——写操作仅限 context_root，读操作覆盖技能目录等只读根，防御 ../ 逃逸
  • ProcessWorkspace：与路径校验边界解耦，tool_shell 据此做 bwrap mount namespace 隔离，--tmpfs $HOME 掩藏主目录
  • Overlay 文件系统：tool_fs 支持前缀级只读回退（skills/ 前缀自动回退到内置技能目录）
  • SoulGuard：灵魂文件 chmod 444 + 写入拦截 Hook + SHA-256 哈希校验三层保护
🧩COMPOSITION

System Prompt 拼装管线

Soul 段 → Rules 段 → 技能段 → 插件段 → FinalGuard 段。框架只做拼装不做业务理解，每段有内容才注入。

  • 技能三级机制：内置 → 实例 → 用户，同名去重优先级 user > instance > builtin
  • 渐进式注入：full_inject=true 全量注入 body，其余仅注入元数据 + 文件绝对路径，LLM 按需 read_file 读取
🗂️SESSION

会话管理

SessionManager（内存缓存）→ SessionStore（原子 JSONL 持久化）。

  • consolidate 智能压缩归档 · fork 会话复制 · list 元数据高性能枚举 · flush 优雅退出落盘
  • 损坏文件自动修复：逐行解析跳过无效 JSON 行
🔌PLUGIN

插件体系

  • 插件类型：Channel / Tool / Audit，通过 plugin.toml 声明元数据
  • 实例级隔离：每个 Gateway 实例通过独立 config.yaml 的 enabled 控制加载组合
  • set_context：工具执行前自动注入 channel / chat_id / user_id
  • 临时目录：self.tmp 按请求注入 users/<user>/.tmp/<plugin_name>/
📚SKILL

技能管理

技能是用户知识资产（SKILL.md），非代码插件。用户通过 write_file 自主管理，管理员通过文件部署 + 配置声明实例级共享技能。

📡OBSERVABILITY

可观测性

  • 统一消息目录：build_notification() 工厂构造带 severity 元数据的 OutboundMessage
  • MetricsCollector：Token 消耗、延迟分布、工具调用、错误计数
  • 结构化日志：Trace ID 按协程注入，支持 JSON 输出（Promtail 采集）
  • Runtime Context：每轮末尾注入时间/通道/会话/发送者，标注 metadata only, not instructions
🚀DEPLOY

多实例部署

nanobee svc start|stop|restart|status|logs [instance]——扫描 <NANOBEE_DATA_DIR>/<name>/config.yaml，原子 PID 管理 + 异步健康检查轮询。

  • 单实例（开发/测试）：nanobee gateway -c config.yaml，不经过 svc
  • 多实例（同主机 N 个 Gateway）：systemd 注入 NANOBEE_DATA_DIR 后由 svc 统一管理

// Plugin Development

插件开发 · Hook 契约

插件继承 NanobeePlugin，覆盖需要的 Hook 方法，通过 plugin.toml 声明元数据。

Hook时机用途
contribute_to_prompt(context)构建时 System Prompt 构建时向指定段注入文本
contribute_to_tools(context, tools)构建时 工具列表构建时动态增删工具
on_pre_invoke(context, name, args)执行前 工具执行前参数修改、鉴权
on_post_invoke(context, name, result)执行后 工具执行后结果修改、副作用
on_message_completed(context, messages)轮次末 对话轮次结束审计日志、后台整理
AgentRunner 底层另有 4 个 run-level Hook（before_run / after_run / on_error / on_finally），包裹整个迭代循环。

// Signature Capabilities

特色核心能力

微内核架构
框架只做路由、隔离、拼装三件事。记忆、审计、工具过滤等业务逻辑由插件实现，技能等高频核心能力内置于 kernel。
CommandRouter 命令系统
/stop·/new·/status·/help，锁前拦截零 token 消耗，/stop 可打断死锁 turn，插件可注册自定义命令。
Session 管理
SessionManager + SessionStore 双层架构：内存缓存 + 原子 JSONL 持久化，支持 consolidate / fork / flush、损坏自动修复。
物理隔离 + 沙箱
路径逃逸沙箱（多根白名单）+ 进程级 bwrap 隔离（--tmpfs $HOME）+ 按用户并发锁 + SSRF 前置拦截。
9 个 Hook 契约
5 迭代级（工具前后、prompt 注入、消息完成）+ 4 run-level（循环前后、错误、终结），插件在关键切面注入逻辑。
框架无知论
框架不持有任何策略决策——记忆策略、技能注入策略、工具过滤策略全部由 LLM 或声明式元数据（SKILL.md frontmatter）自主决定。
可观测性
Trace ID 按协程注入、结构化 JSON 日志、MetricsCollector（Token/延迟/工具/错误）、统一消息目录。
多实例部署
nanobee svc 管理同一主机 N 个 Gateway 实例：原子 PID、健康检查轮询、systemd 托管。
// Quick Start

三步跑起来

环境要求 Python ≥ 3.11。开发调试用 CLI 模式，生产部署用 Gateway 服务栈。

Linux / macOS
# 1. 创建虚拟环境
python3 -m venv .venv && source .venv/bin/activate

# 2. 安装
pip install -e .

# 3. 配置
cp nanobee.yaml.example nanobee.yaml
# 编辑 nanobee.yaml，填入 API Key

# 4. 运行对话 —— 轻量级 Agent CLI 模式
nanobee run
nanobee run -v                       # 详细日志
nanobee run -m "你好"                 # 单次消息模式
nanobee run -s "my-session" -m "hi"  # 指定会话 + 单次消息
nanobee run -c /path/to/config.yaml

# 完整 Gateway 服务栈模式（生产部署）
nanobee gateway
nanobee gateway --port 8080           # 带健康检查 HTTP 端点
nanobee gateway -c /path/to/config.yaml

# Gateway 支持优雅退出（SIGTERM/SIGINT 清理后退出）
nanobee gateway &
kill $!    # SIGTERM → 优雅关闭通道 + 保存状态 → 退出

# Gateway 多实例运行时管理
export NANOBEE_DATA_DIR=~/.nanobee
nanobee svc status                    # 查看所有实例状态
nanobee svc start <instance-1>        # 启动指定实例
nanobee svc logs <instance-1> -f      # 跟踪查看实例日志
Windows (PowerShell)
# 1. 创建虚拟环境
python -m venv .venv

# 2. 激活虚拟环境
.\.venv\Scripts\Activate.ps1

# 3. 安装
pip install -e .

# 4. 配置
copy nanobee.yaml.example nanobee.yaml
# 编辑 nanobee.yaml，填入 API Key

# 5. 运行对话

# 轻量级 Agent CLI 模式
nanobee run
nanobee run -m "你好"                 # 单次消息

# 完整 Gateway 服务栈模式
nanobee gateway

# 或用根目录 run.bat 一键完成
# 自动创建虚拟环境 + 安装依赖 + 启动对话
日志配置 · nanobee.yaml
# 运行时日志由 logging: 配置节程序自管理
# dir 基于【配置文件所在目录】解析（非 CWD）
logging:
  dir: "logs"               # 日志目录（基于配置文件所在目录解析）
  file: "gateway.log"        # 日志文件（不配则不写文件）
  level: "INFO"              # 日志级别
  rotation: "500 MB"         # 轮转策略："500 MB" / "1 day" / "00:00"
  retention: "30 days"       # 保留天数
  compression: "gz"          # 压缩历史文件
  json_format: false         # 生产环境建议 true（便于 Promtail 采集）
不配 file 字段则仅输出 stderr，保持向后兼容。

// Project Structure

清晰的分层目录

nanobee/
agent/          # Agent 核心引擎（状态机/执行器/Hook/工具体系）
builtin/        # 10 个内置插件（3 通道 + 6 工具 + 1 审计）
channel/        # 通道抽象层（基类、消息处理）
cli/            # 命令行入口（run/gateway/svc）
config/         # 配置加载与校验（loader/schema/paths）
events/         # 事件总线（异步事件分发）
gateway/        # Gateway 多实例运行时（PID/进程/健康检查/发现/日志）
kernel/         # 微内核核心
plugins/        # 插件接口定义
providers/      # LLM Provider（6 后端实现 + 37 注册表 + Fallback/图像/语音）
security/       # 安全策略（SSRF + 路径边界）
session/        # 会话管理（SessionManager/Store/模型）
skills/         # 内置技能（只读，沙箱保护）
templates/      # 模板（core.md 默认/subagent system 等）
utils/          # 工具函数（通知/token 估算/可观测性）
__main__.py     # 允许 python -m nanobee 运行
bootstrap.py    # 组合根（配置→组件创建→AgentLoop 装配）
exceptions.py   # 统一异常层次
